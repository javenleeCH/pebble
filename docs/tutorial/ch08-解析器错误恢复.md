# 第 8 章 解析器错误恢复：一次报出所有错误

> 对应文件：`crates/pebble-parser/src/{lexer.rs, parser.rs}`、`crates/pebble-diagnostic/src/lib.rs`、`crates/pebble-driver/src/{lib.rs, main.rs}`；规范：`docs/draft/spec/08-diagnostics.md` §8.6。
> 测试：`crates/pebble-parser/tests/recovery.rs`（恢复矩阵）、`crates/pebble-driver/tests/diagnostics.rs`（报错全文的契约）。

## 本章目标

1. 说清楚「遇到第一个错误就停」为什么是**最简单的正确做法**，以及它的代价；
2. 学会教科书里的 **panic-mode 恢复**，并为 Pebble 找到它自己的**同步点**；
3. 认识错误恢复真正的难点——**级联错误**，以及堵住它的办法：同步点、残骸模式、阶段门控；
4. 修一个真实的 bug：中文注释会让编译器定位漂移、甚至直接崩溃。由此理解「**Span 的单位是契约**」；
5. 把「用户看到的报错全文」变成可以被测试断言的数据；
6. 记住递归下降的代价：它靠调用栈记状态——所以凡是递归处理用户输入的地方，都要给深度设上限。

前 7 章里，解析器一直是「一错即停」的。这一章结束之后：

| | 第 8 章之前 | 第 8 章之后 |
|---|---|---|
| 一个文件里有 N 个语法错误 | 每次编译只报第 1 个 | 一次报出，按源码位置排序。*拿不准是不是前一个错误的残骸时，宁可少报*（见「代码走读」第 3 节） |
| 词法错误 + 语法错误 | 只报词法错误 | 都报 |
| 行尾漏写 `)` | 在下一个算子处报一条让人摸不着头脑的消息，然后停止 | 报在下一个算子处并提示成因；其后的算子照常解析 |
| 中文注释之后的错误 | 定位漂移，或者编译器崩溃（退出码 101） | 定位准确 |
| 一行里上万个非法字符 | 渲染一分钟以上 | 瞬间完成；最多显示 100 条，汇总行给出真实总数 |
| 100 层嵌套的表达式 | 编译器栈溢出崩溃 | 一条诊断：「表达式嵌套过深」 |
| 输出结尾 | 无 | `编译中止：共 N 个错误（LEX x，PAR y）` |

## 为什么：首错即止错了吗？

没有错。回看第 2 章：每个解析函数返回 `Option<T>`，出错就 `return None`，调用方用 `?` 一路上抛。第一个错误一出现，整棵树的构造立刻停止——**没有任何下游代码会看到半棵树**。正确、简单、不会出诡异的 bug。

代价在使用体验上。这个文件两行各有一个错误：

```pebble
Table("tests/data/orders.csv") as o
  .filter(o.amount > )
  .select(o.customer_id + )
  .collect()
```

第 8 章之前的编译器只报第 2 行，然后停下：

```text
error[PAR-001]: 期望表达式，遇到 `)`
  ┌─ two-errors.pebble:2:22
  │
2 │   .filter(o.amount > )
  │                      ^ PAR-001
  │
```

第 3 行还有一模一样的错误，要等改完第 2 行、重新编译才看得见。N 个错 = 编译 N 次。

### 那不停不就行了？

试试最天真的做法：词法层遇到 `^` 报个错、把它扔掉，解析器若无其事地继续。于是解析器看到的是 `o.amount  2 > 1`——`o.amount` 之后无缘无故冒出一个 `2`，它只能报「期望 `)`，遇到 整数 `2`」。

这个「期望 `)`」就是**级联错误（cascading error）**：它不是用户犯的错，而是前一个错误留下的残骸被当成了新错误。对一个把「可信」当卖点的编译器，假错误的代价尤其高——用户被误导两次之后就会开始忽略诊断，真错误也跟着被忽略。

所以本章的全部设计只服从一条原则：

> **一个根因只报一次。拿不准是不是残骸时，宁可少报，不可多报。**

### 被否决的备选

| 方案 | 为什么不行 |
|---|---|
| 维持首错即止 | 正确，但 N 个错要编译 N 次 |
| 出错就跳到下一行 | Pebble 不看换行：一个算子可以写多行（`.agg(` 里一个绑定一行）。按行切会把好端端的算子切碎，报出一串假错误 |
| 出错就跳到下一个 `.` | `o.amount` 里也有 `.`，跳过去等于把表达式拦腰截断 |
| 只数括号深度，不认括号种类 | `if c { f(a + }` 里那个 `}` 属于外层。把它当成 `f(` 的右括号，后面的 `else` 就会被误判成错误 |
| 有词法错误就不解析 | 词法错误和语法错误互相独立；何况词法层扔掉坏 token 之后，解析器必然报出级联的「期望 `)`」 |
| 恢复出来的 AST 继续做语义检查 | 坏算子改变了后面的字段集合，下游的「字段不存在」全是假警报。要等第 9 章的毒化类型 |
| 换 Chumsky（`recover_with`） | 框架给的只是机制。同步点选在哪、怎么防级联，照样得自己想（第 2 章） |

## 代码走读

### 1. 先画围栏地图：同步点在哪

**panic-mode 恢复**用一句话就能说完：出错之后丢弃 token，直到遇到一个**一定能重新开始解析的位置**——同步点（synchronization point）。

教科书不会告诉你同步点选在哪，那是每种语言自己的事，得**从文法里读出来**。问自己：Pebble 里，哪些位置无论前面坏成什么样，都能肯定「一个新结构从这里开始」？

| 围栏 | 同步点 | 丢掉什么、保住什么 |
|---|---|---|
| 1 | 列表里的 `,` | 丢一个元素，保住同一个列表的其他元素 |
| 2 | 当前层的右括号 `)` / `}` | 丢一个算子、一次调用或一个括号表达式 |
| 3 | 下一个算子的起点 | 丢掉整段残骸，回到流水线层 |

三道围栏里有两处不显然，值得停下来想。

**`o.amount` 里也有 `.`，怎么知道哪个是下一个算子？** 往后多看两个 token。合法的表达式里不存在「`.` 标识符 `(`」这种写法——表达式里的 `.` 只用于 `别名.字段`，而 Pebble 没有方法调用。所以只要 `.` 后面紧跟「标识符 + `(`」，它就**只可能**是下一个算子：

```rust
    /// `peek()` 之后是否紧跟 `标识符 (`。
    fn is_op_call_ahead(&self) -> bool {
        self.op_name_ahead().is_some()
            && matches!(
                self.toks.get(self.pos + 2),
                Some(Token {
                    tok: Tok::LParen,
                    ..
                })
            )
    }
```

反过来同样重要：同步时**只**相信这个形状。`.filter o.a > 1)`（少了左括号）里 `o.a` 的 `.` 落在深度 0；把它也当成算子起点，就会多报一条「未知算子 `a`」。（这个 bug 是恢复矩阵抓出来的，见文末「踩坑实录」。）

而到了后面要讲的**残骸模式**，连这个形状也不能全信：只认已知的算子名。

**深度怎么知道？用括号栈。** 每读一个 `(`/`{` 入栈，每读一个 `)`/`}` 出栈——栈高就是深度，不必另外计数：

```rust
    fn advance(&mut self) -> Token {
        let t = self.toks[self.pos.min(self.toks.len() - 1)].clone();
        if self.pos < self.toks.len() - 1 {
            match t.tok {
                Tok::LParen | Tok::LBrace => self.brackets.push(t.tok.clone()),
                Tok::RParen | Tok::RBrace => {
                    // 右括号关掉与它配对的最内层开括号；中间没闭合的层一并关掉
                    let opener = if t.tok == Tok::RParen {
                        Tok::LParen
                    } else {
                        Tok::LBrace
                    };
                    if let Some(k) = self.brackets.iter().rposition(|b| *b == opener) {
                        self.brackets.truncate(k);
                    }
                }
                _ => {}
            }
            self.pos += 1;
        }
        t
    }
```

出栈那几行是关键：右括号找的是「与它**配对**的最内层开括号」，而不是简单地弹出栈顶。`if c { f(a + }` 里那个 `}` 属于外层的 `{`，`f(` 其实还没闭合——栈如实记下这件事，后面收尾的人才不会张冠李戴。

围栏画好之后，同步本身就只有几行：

```rust
    fn sync_to(&mut self, base: usize) {
        loop {
            if *self.peek() == Tok::Eof {
                self.brackets.clear();
                break;
            }
            if self.at_operator_start() {
                break;
            }
            let is_separator =
                *self.peek() == Tok::Comma || matches!(self.peek(), Tok::RParen | Tok::RBrace);
            if is_separator && self.depth() <= base {
                break;
            }
            self.advance();
        }
    }
```

循环体只有两种结局：命中围栏就 `break`，否则 `advance()`。注意里面**没有任何 `diags.error`**——被跳过的 token 是残骸，不是错误。「比 `base` 更深的括号整组吞掉；`base` 层的右括号不消费」这两个细节，交给练习 3。

### 2. `None` 换了一个含义

第 2 章的解析函数签名一行没改，`?` 也到处照用。变的是 `None` 的**语义**：

| | 第 2 章（首错即止） | 第 8 章（恢复） |
|---|---|---|
| `None` 的含义 | 出错了，放弃 | 这一段坏了；错误已报告，位置已同步到围栏 |
| 谁接住 `None` | 最外层的 `parse()` | 离得最近的循环：流水线循环或列表循环 |
| 接住之后 | 返回 `None` | 丢弃这一段，继续下一项 |

要让这个新含义成立，「错误已报告」和「位置已同步」必须永远一起发生。办法是把两件事焊在同一个函数里：

```rust
    fn fail_spanned(
        &mut self,
        code: Code,
        message: impl Into<String>,
        span: Span,
        hint: Option<&str>,
    ) {
        let mut d = pebble_diagnostic::Diagnostic::error(code, message, span);
        if let Some(h) = hint {
            d = d.with_hint(h);
        }
        self.diags.push(d);
        let base = self.depth();
        self.sync_to(base);
    }
```

于是全文件的纪律只有一条：**报告错误的代码必须同步；返回 `None` 的其他代码什么都不做。** `fail` / `fail_hint` / `fail_at` 都是它的薄封装。

### 3. 两处接住 `None` 的地方

**流水线循环**是粗粒度的恢复点。坏掉的算子整个丢弃，循环本身从不 `return`：

```rust
        // 流水线循环 = 流水线层的恢复点：坏掉的元素整个丢弃，绝不中断整条流水线。
        // 深度 0 上的任何 `.` 都只能是下一个算子的起点。
        loop {
            if *self.peek() == Tok::Error {
                self.advance();
                continue;
            }
            if *self.peek() == Tok::Eof {
                break;
            }
            if *self.peek() != Tok::Dot || self.depth() != 0 {
                // 流水线层冒出了一个不该有的 token。报一次，然后跳到下一个算子**继续**——
                // 后面的算子里可能还有独立的错误，不能因为一个多余的 `)` 就都不看了
                let got = describe(self.peek());
                let span = self.peek_span();
                self.diags.error(
                    Code::ParUnexpected,
                    format!("流水线在这里中断：多出了一个 {got}"),
                    span,
                );
                self.sync_pipeline();
                continue;
            }
```

用新手最常见的笔误——行尾漏写 `)`——走一遍：

```pebble
Table("a.csv") as o
  .filter(o.amount > 100
  .collect()
```

| # | 读到 | 括号栈（深度） | 发生了什么 |
|---|---|---|---|
| 1 | `.filter(` | `.filter(`（1） | 进入算子 |
| 2 | `o.amount > 100` 之后的 `.` | `.filter(`（1） | `parse_postfix` 往后看：`collect` `(` → 这是一个算子的起点 → **PAR-001**，报在 `.` 上并附提示；同步：已经在围栏上，原地停住 |
| 3 | 同上 | `.filter(`（1） | `None` 上抛：`parse_postfix` → `parse_add` → … → `parse_operator`，沿途**没有任何人再报告** |
| 4 | 同上 | `.filter(`（1）→ 空 | 流水线循环接住 `Element::Broken`。`sync_pipeline` 发现括号栈非空：被越过的 `(` 就地视作闭合，并进入**残骸模式**（下一小节） |
| 5 | `.collect()` | 空（0） | 残骸模式下先试探着解析：`collect` 是已知算子名，解析完紧跟文件结尾——像那么回事，留下 |
| 6 | 文件结尾 | — | 再同步一次，吞掉迟到的右括号（本例没有） |

实际输出：

```text
error[PAR-001]: 表达式内部出现了 `.collect(`
  ┌─ missing-paren.pebble:3:3
  │
3 │   .collect()
  │   ^ PAR-001
  │
  提示: 表达式里的 `.` 只能用于 `别名.字段`，不能调用方法；如果这其实是下一个算子，说明前面的 `(` 缺少 `)`
编译中止：共 1 个错误（PAR 1）
```

#### 残骸：恢复出来的东西，不一定是对的

上面的例子藏着一个没说破的假设：`.collect()` 真的是下一个算子。可它也可能只是没闭合的表达式的一部分。比如按别的语言的习惯写了方法调用：

```pebble
Table("a.csv") as o
  .filter(o.rows.collect() > 1)
  .select(o.order_id)
```

第一个错误报出之后，`.collect(` 看起来**完全**像一个算子的起点。照单全收的话，它就成了流水线的终端，后面那个无辜的 `.select` 会被报成「终端算子之后不得再接续任何算子」——一个由恢复方式自己制造出来的错误。

所以循环的后半段不急着当真：

```rust
            // 残骸模式下的元素是试探性的：它产生的诊断先记着，等确认它真的像一个算子再说
            let mark = self.diags.diags.len();
            let after_terminal = terminal.is_some();
            let element = self.parse_element(after_terminal);
            if self.debris && !self.ends_like_pipeline_element() {
                // 这个「算子」其实是没闭合的表达式的一部分：连同它的诊断一起丢弃
                self.diags.diags.truncate(mark);
                self.sync_pipeline();
                continue;
            }
            match element {
                Element::Op(o) => {
                    // 终端之后的算子照常解析（为了找出里面独立的错误），但不进 AST
                    if !after_terminal {
                        end = o.span();
                        ops.push(o);
                    }
                }
                Element::Terminal(t) => {
                    if terminal.is_none() {
                        end = t.span();
                        terminal = Some(t);
                    }
                }
                Element::Broken => self.sync_pipeline(),
            }
            if self.debris {
                // 吞掉迟到的右括号等残骸，停在下一个算子前
                self.sync_pipeline();
            }
        }
```

三个要点：

1. **残骸模式**（`debris`）。`sync_pipeline` 停下时如果括号栈非空，说明它是在未闭合的括号里遇到下一个算子的。从此以后同步只相信**已知**的算子名——`.abs(` 这种直接当残骸跳过——并且每个元素都先试探着解析。
2. **试探**是一个小事务：先记下已经有几条诊断（`mark`），解析完看它以什么收尾。一个真正的算子之后只该是：文件结尾、下一个算子的起点、或者几个迟到的右括号之后的这两者（`ends_like_pipeline_element`）。`.collect()` 后面跟着 `>`：不像。于是 `truncate(mark)` 撤回它产生的诊断，元素本身也丢掉。
3. **一旦进入，保持到文件结尾。** 代价是：这之后如果真的有一个拼错的算子名，这一次不会报出来，要等漏括号修好后的下一次编译。这是「拿不准时宁可少报」的又一次取舍。

实际输出只有一个错误，`.select` 没有被牵连：

```text
error[PAR-001]: 表达式内部出现了 `.collect(`
  ┌─ debris-collect.pebble:2:17
  │
2 │   .filter(o.rows.collect() > 1)
  │                 ^ PAR-001
  │
  提示: 表达式里的 `.` 只能用于 `别名.字段`，不能调用方法；如果这其实是下一个算子，说明前面的 `(` 缺少 `)`
编译中止：共 1 个错误（PAR 1）
```

#### 两条不那么显眼的规则

都在循环的前半段里，方向却和「少报」相反——**独立的错误一个不能漏**。

**流水线层多出了一个 token**，比如多敲了一个 `)`。以前这里报「期望文件结尾」就停了，第 3 行那个真正的错误要等下一次编译。现在报一句「流水线在这里中断」，跳到下一个算子**继续**：

```text
error[PAR-001]: 流水线在这里中断：多出了一个 `)`
  ┌─ stray-paren.pebble:2:19
  │
2 │   .filter(o.a > 1))
  │                   ^ PAR-001
  │
error[PAR-001]: 期望表达式，遇到 `)`
  ┌─ stray-paren.pebble:3:16
  │
3 │   .select(o.b +)
  │                ^ PAR-001
  │
编译中止：共 2 个错误（PAR 2）
```

**终端之后又接了算子**（PAR-002）。这条只报一次；但后面的算子照常解析，只是不进 AST。`.collect()` 后面那个 `.filter(o.typo > )` 里漏写的操作数，和 PAR-002 毫无关系，不该被它吞掉。

**列表循环**是细粒度的恢复点，由通用骨架 `parse_list` 统一处理（select 项、sort 键、agg 绑定、记录绑定、调用实参都用它）：

```rust
        loop {
            let item_start_span = self.peek_span();
            let item_diags = self.diags.diags.len();
            match elem(self) {
                Some(e) => out.push(e),
                None => {
                    // 这条诊断报在元素的第一个 token 上 = 元素还没读进任何东西就失败了
                    let failed_on_first_token = self
                        .diags
                        .diags
                        .get(item_diags)
                        .is_some_and(|d| d.span == Some(item_start_span));
                    if damaged && failed_on_first_token {
                        // 紧跟在坏元素后面、一个 token 都没读进去就失败的元素，多半是前者被逗号截断的残骸
                        //（`x = if a >, 0 { 1 }`：`0 { 1 }` 其实还是那个 if 的一部分）。连它的诊断一起丢弃
                        self.diags.diags.truncate(item_diags);
                    }
                    // 先吞掉内层没闭合的右括号，看能否回到本列表所在的层
                    while self.depth() > my_depth
                        && matches!(self.peek(), Tok::RParen | Tok::RBrace)
                    {
                        self.advance();
                    }
                    // 回不来：本列表的括号已被更外层的恢复越过（或已到文件结尾）
                    if self.depth() != my_depth {
                        return None;
                    }
                    // 回来了：这一项连同它后面残留的 `as x` 之类一起丢掉，停到 `,` 或右括号
                    damaged = true;
                    let base = self.depth();
                    self.sync_to(base);
                }
            }
            if self.accept_punct(&Tok::Comma) {
                if self.peek() == closing {
                    break; // 尾逗号
                }
                continue;
            }
            break;
        }
```

先是**判断自己还有没有资格继续**：那个 `if self.depth() != my_depth { return None; }`。`None` 上抛到列表时，自己的括号还在（深度没变）→ 接住，丢掉这个元素；自己的括号已经被更外层的恢复越过 → 我也坏了，继续上抛。

列表里也有残骸，只是形状不同。条件里多打了一个逗号：

```pebble
Table("a.csv") as o
  .extend({
    x = if o.amount >, 0 { 1 } else { 2 },
    y = 2,
  })
  .collect()
```

第一个错误报在逗号上：`>` 后面缺操作数。列表接住它、吃掉逗号，接着把 `0 { 1 } else { 2 }` 当成了**下一个**绑定——于是又报一条「期望记录绑定名，遇到 `0`」。可那分明还是刚才那个 if 的后半截。

这就是循环开头那九行的作用：如果某个元素**还没读进任何东西就失败了**（判断依据是「它的诊断报在它自己的第一个 token 上」），而紧挨在它前面的元素刚坏过，那它多半是被逗号截断的残骸，连诊断一起丢弃。边界要划清楚：两个各自写错的相邻绑定（`a = o.x +,` 和 `b = o.y +,`），第二个是读进了 `b = o.y +` 才失败的，属于独立的错误，照常各报各的。

再看一个例子，两个坏绑定夹着一个好绑定：

```pebble
Table("a.csv") as o
  .agg(
    a = sum(o.x),
    b = 1 + 1,
    c = count(),
  )
  .collect()
```

| # | 读到 | 括号栈（深度） | 发生了什么 |
|---|---|---|---|
| 1 | `a = sum(o.x)` | `.agg(`（1） | 第 1 个绑定解析成功 |
| 2 | `b =` 之后的 `1` | `.agg(`（1） | `parse_agg_call` 发现右侧不是聚合调用 → **PAR-005**；同步跳过 `1 + 1`，停在 `,` 前 |
| 3 | `,` | `.agg(`（1） | `None` 上抛到 `parse_list`。深度 1 = 列表自己的深度 → **接住**：丢掉 `b`，`damaged = true` |
| 4 | `,` 之后 | `.agg(`（1） | 吃掉逗号，`c = count()` 解析成功。它读进了 `c =` 才开始解析，不是残骸 |
| 5 | `)` | 空（0） | 收尾：列表坏过，右括号在就吃掉，**不再报错** |

第 5 步是「一个根因只报一次」的最后一道保障：坏过的列表收尾时如果找不到右括号，那是第一个错误的后果，静默放弃即可。

**表达式层没有恢复点。** `parse_add`、`parse_or` 这些函数拿到 `None` 原样上抛——接住它的，是拥有「这道括号」的那一层。

#### 别把调用栈撑爆

递归下降解析器靠**调用栈**记状态：输入嵌套多深，栈就有多深。所以 `((((…1…))))` 嵌套 100 层、`-----…-1`、3000 层的 `else if`，编译器不会报错——它会**崩溃**：栈溢出，一条诊断都没有。（这个问题第 8 章之前的代码里就有；是一份独立评审用一堆「又深又长」的输入找出来的。）

解决办法朴素得有点好笑：数着点。

```rust
    /// 深入一层表达式递归。超过上限时报 PAR-001 并返回 `None`（由调用方用 `?` 接住上抛）。
    fn descend(&mut self, f: impl FnOnce(&mut Self) -> Option<Expr>) -> Option<Expr> {
        self.nesting += 1;
        let result = if self.nesting > MAX_NESTING {
            self.fail(
                Code::ParUnexpected,
                format!("表达式嵌套过深（最多 {MAX_NESTING} 层）"),
            );
            None
        } else {
            f(self)
        };
        self.nesting -= 1;
        result
    }
```

凡是函数递归调用自己的地方——括号、一元 `-` 和 `!`、`else if` 链——都经过 `descend`，超过 `MAX_NESTING`（64 层）就报「表达式嵌套过深」：

```text
error[PAR-001]: 表达式嵌套过深（最多 64 层）
  ┌─ limit-depth.pebble:2:75
  │
2 │   .filter(((((((((((((((((((((((((((((((((((((((((((((((((((((((((((((((((((((((1)))))…
  │                                                                           ^ PAR-001
  │
编译中止：共 1 个错误（PAR 1）
```

（上面那行源码为了排版截短了。）还有另一个上限，防的是另一种「深」：`1 + 1 + 1 + …` 写上一万项并不嵌套，却会造出一棵一万层深的树。解析它不需要递归，但之后**释放**这棵树的时候 Rust 会一层层递归下去，同样会撑爆栈。所以每个表达式还限定原子个数（`MAX_ATOMS`，256 个）。

上限具体是多少并不重要。重要的是这条规矩：**凡是靠递归处理用户输入的地方，都要给递归深度设一个上限。**

### 4. 词法层留便条：`Tok::Error`

回到「那不停不就行了」里那个 `^`。问题不在「继续解析」，而在词法层**悄悄扔掉**了坏 token，留下一个解析器看不见的窟窿。

办法是留一张便条：

```rust
    /// 词法层留下的「洞」：这里有一个无法识别的 token，词法层**已经报过错**。
    /// 它占住位置，使 token 流的结构不变；解析器遇到它绝不重复报错（第 8 章）。
    Error,
```

解析器这边只有一条规则——遇到便条就闭嘴：

```rust
    fn eat_hole(&mut self) -> bool {
        if *self.peek() != Tok::Error {
            return false;
        }
        self.advance();
        let base = self.depth();
        self.sync_to(base);
        true
    }
```

`expect_punct`、`expect_ident`、`parse_primary` 在报告任何错误之前都先问一句 `eat_hole()`。

词法层自己也尽量**少留洞**：能救回值的就救回值，让 token 流的结构保持完整。

| 写法 | 第 8 章之前 | 现在 |
|---|---|---|
| `1.` | 报 LEX-004，但不产生任何 token——token 流上留下窟窿 | 报 LEX-004，救回整数 `1`，窟窿补上 |
| `.5` | 报 LEX-004，整个 `.5` 跳过——同样留窟窿 | 报 LEX-004，只越过 `.`，`5` 下一轮照常识别成整数 |
| `"a\qb"` | 报 LEX-003，字符串本身保留 | 不变 |
| `"abc`（未闭合） | 报 LEX-002，不产生 token | 报 LEX-002，留一个洞占位 |

第 8 章之前，解析器一看到词法错误就根本不运行，所以这些窟窿从没造成过看得见的后果。可本章必须让解析器在有词法错误时继续工作——窟窿不补，它们就全变成级联错误。**一个被别的保守策略掩盖着的隐患，在你放松那道策略的那一刻就会现形。**

顺手还做了两件对中文用户格外友好、成本却极低的事：跳过文件开头的 UTF-8 BOM（Windows 编辑器常加）；全角标点（`（` `，` `：` `“`……）提示「请改用半角」。后者值得多说一句——中文输入法下这类笔误很常见，而全角和半角在等宽字体里只差一点点，肉眼几乎发现不了；一条针对性的提示能省掉半小时的瞪眼。对不可见的字符（控制字符、不换行空格）则报出码点 `U+0007`，而不是往消息里塞一个看不见的东西。

### 5. 阶段门控进类型：`Result<Program, PartialAst>`

解析器的对外接口从 `Option<Program>` 变成：

```rust
pub fn parse(source: &str, diags: &mut DiagBag) -> Result<Program, PartialAst> {
    // ……词法分析、构造 Parser（节选）……
    let program = p.parse_program();
    if p.diags.has_error() {
        Err(PartialAst {
            program: Box::new(program),
        })
    } else {
        Ok(program)
    }
}
```

`Err` 里装的不是「失败」这两个字，而是恢复出来的**部分 AST**——只含完整解析的算子，可能缺源、缺算子、缺终端。

为什么不让 `parse` 永远返回 `Program`、由调用方自己去看 `diags.has_error()`？因为那样「带伤的树被误交给语义层」只是一个疏忽之遥。现在 `PartialAst` 是另一个类型，它的 `program` 字段是私有的；语义层的入口 `compile()` 只接受 `&Program`。第 2 章说过：**能用类型表达的约束，不要留给检查。**

规范（08-diagnostics §8.6 第 4 条）要求「任一编译期 Error 存在时，不进入 HIR lowering」。现在这条规矩由类型系统代为执行。

顺带一课来自 clippy：`PartialAst` 里的 `Program` 要装进 `Box`。`Result` 的大小取决于较大的那个变体，一整棵树按值塞进 `Err`，会让每次 `parse` 调用都背着几百个字节。

### 6. 一个真实 bug：Span 的单位是契约

写这一章时，我重读第 3 章的渲染器，注意到 `locate` 里 `for (i, ch) in source.char_indices()` 的 `i` 是**字节**下标，却被拿去和 Span 直接比较——而第 1 章的词法层记的是**字符**下标。读代码时产生的怀疑，要用最小复现去证实。只需两行：

```pebble
//中文
 x
```

```text
thread 'main' panicked at crates\pebble-diagnostic\src\lib.rs:260:24:
end byte index 6 is not a char boundary; it is inside '文' (bytes 5..8 of string)
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

（线程号已略去。）用户只是把 `Table` 写漏了，本该得到「流水线必须以 Table 或 MemoryTable 开头」，得到的却是 Rust 的 panic，退出码 101。本章的演示文件——开头两行中文注释——同样崩溃：`end byte index 132 … inside '法'`。

根因只有一句话：**两个模块对同一个数字的单位理解不同。** 第 1 章的词法层按**字符**计数记录 Span；第 3 章的渲染器 `locate` 却把它当**字节**偏移去切片。源码全是 ASCII 时两者相等，于是相安无事——直到第一个汉字出现：

```text
字符:  /     /     中              文
下标:  0     1     2               3           ← 词法层记的「字符下标」
字节:  2F    2F    E4  B8  AD      E6  96  87
偏移:  0     1     2   3   4       5   6   7   ← 渲染层以为的「字节偏移」
```

一个汉字 3 个字节、1 个字符。每多一个汉字，渲染器的理解就比真实位置少 2：轻则框错地方，重则切在某个字节中间，`&source[start..end]` 直接 panic。

**修法**是让双方统一到字节偏移（教科书做法，也是 `Span` 的文档注释一开始就写的）。词法层扫描仍然按字符走——简单直观——只在写 Span 的地方查一张换算表：

```rust
    let bytes: Vec<char> = source.chars().collect();
    // 字符下标 → 字节偏移。扫描按字符走（简单直观），但 Span 必须写成字节偏移：
    // 渲染层用 `&source[start..end]` 切片，而 Rust 字符串是按字节索引的。
    let mut byte_at: Vec<usize> = source.char_indices().map(|(b, _)| b).collect();
    byte_at.push(source.len());
```

显示给用户的列号仍然按字符数（`chars().count()`），一个汉字算一列。

另外两处顺手加固：

- **渲染器是最后一道防线。** `locate` 现在先把偏移夹取到合法的字符边界上（`clamp_to_boundary`），再离谱的 Span 也只会框错地方，不会 panic。报错的代码自己崩溃，用户就什么都看不到了。
- **跨行的 Span 只标注第一行。** 以前一个横跨多行的算子会让 `^` 冲出一整行。

注意 Span 的单位变了、数值全变了，但 HIR 哈希纹丝不动——Span 本来就不进 canonical 序列化（第 5 章）。`non_ascii_comments_change_spans_but_not_the_hash` 这个测试专门钉住这一点。更直接的证据来自新旧两版编译器的实测：对 `examples/` 下全部 7 个样例，各自产出的 6 种文件（canonical HIR、`plan.sql`、manifest……）共 42 个，**逐一字节相同**。

这个 bug 能在第 8 章之前全绿的 43 个测试眼皮底下活着，是因为所有测试源码都是 ASCII。**测试没有覆盖的输入，就是没有测试。**

### 7. 最后一公里：排序、去重、汇总行

诊断是按「发现顺序」收集的，人读的是「源码顺序」。两者可能不同——比如第 1 行有语法错误、第 5 行有词法错误时，词法错误先被发现。所以渲染之前先整理：

```rust
    pub fn normalize(&mut self) {
        self.diags.sort_by_key(|d| {
            d.span
                .map(|s| (s.start, s.end))
                .unwrap_or((usize::MAX, usize::MAX))
        });
        self.diags.dedup();
    }
```

排序是稳定的（同一位置保持发现顺序）；没有源码位置的 RUN 诊断排到最后；完全重复的条目去掉。`render_all` 先整理再逐条渲染，末尾附一行汇总：

```text
编译中止：共 3 个错误（LEX 1，PAR 2）
```

类别顺序固定按编译阶段 LEX → PAR → SEM → SCH → RUN，与发现顺序无关。

多错误报告带来了一个第 3 章没有的问题：**性能**。渲染一条诊断要知道「偏移在第几行」，第 3 章的写法是每条都把源码从头扫一遍。只报一条错误时无所谓；一次报一万条，代价就是「诊断数 × 文件大小」——一行里一万个非法字符，要扫上亿次。独立评审实测：50 000 个非法字符的文件，一分钟以上都出不来。

修法是查找表：把每行的起始偏移建成一张有序表，定位行号变成一次二分查找。

```rust
    /// 偏移 `offset` 所在的行（0 开始）：最后一个起点不晚于它的行。
    fn line_of(&self, offset: usize) -> usize {
        self.starts.partition_point(|&s| s <= offset) - 1
    }
```

`render_all` 只建一次表，所有诊断共用。另外它一次最多显示 `MAX_RENDERED`（100）条，其余的写一行「另有 N 条未显示」——没人读得完一万条，但汇总行里的数字必须是真实的总数。**「少显示」和「少报」是两回事**：前者只影响你看到多少，后者影响编译器知道多少。

最后一步在 driver：`CompileFailure` 从「一个退出码」变成「退出码 + 报告全文」，库函数不再自己 `eprintln!`。

```rust
#[derive(Debug)]
pub struct CompileFailure {
    pub code: u16,
    pub report: String,
}
```

打印交给 `main`。这样一来，「用户到底看到了什么」成了一个普通的 `String`，可以被测试断言：`crates/pebble-driver/tests/diagnostics.rs` 核对的是本章「跑起来」那份输出的位置、提示与汇总行；`docs_gate` 则把全文与教程**逐字**比对——教程里贴一段过期的输出，CI 就红灯。

### 踩坑实录

这一章的开发里，恢复矩阵、一份独立评审和两个工具链上的 clippy 各抓到过实现的真实缺陷。值得记下来的不是「有 bug」，而是**怎么对待「测试失败」和「别人说你有 bug」**。

**1. 列号别手数。** 恢复矩阵的断言是「完整的错误列表：码 + 行 + 列」。我有 5 次把期望的列号数错了。数错本身不要紧——要紧的是面对「期望与实际不一致」时的态度：如果一看到不一致就改期望值，就会把真 bug 一起放过。每次不一致，我都先把实际的 token 和 Span 打印出来，再判断是哪一侧错了。数错了就改期望；实现错了就改实现。后来我给测试加了一个 `pos(src, needle)`：期望的行列由源码里的子串直接算出来，从此不再手数。

**2. 两个真 bug 都是矩阵抓出来的。**

- 流水线循环最初用「当前括号深度是否大于 0」判断「是不是刚越过了一个没闭合的括号」。但走到那里时括号栈已经被 `sync_pipeline` 清空——信息丢了。`.select(o.a, o.b` 后面接 `.sort(o.a))`，迟到的 `)` 被报成「期望文件结尾」。修法：谁清空栈，谁负责把这件事记下来。（这个标记后来发展成了上面讲的残骸模式。）
- 同步曾把深度 0 上的任何 `.` 都当成下一个算子。`.filter o.a > 1)` 里 `o.a` 的 `.` 就这样把 `a` 变成了「未知算子」。修法：同步只相信 `.标识符(` 这个形状。

教训和附录 A 一样：**门禁先于人类发现真实缺陷。** 没有那张「必须恰好这些错误、一个不多一个不少」的矩阵，这两个 bug 会活到用户面前。

**3. 新手视角的试跑抓到第三个。** 我把 12 种最常见的笔误挨个跑了一遍。`o.amount.abs()`（按别的语言的习惯写方法调用）报了两条：第二条「未知算子 `abs`」正是恢复方式自己制造的级联。自动化测试想不到的输入，把常见的都手工跑一遍就出来了。——但现在你可以猜到，这个修法只修了一半。

**4. 一条「失败也算通过」的检查，不是检查。** 我想证明 Span 单位的改动没有影响任何产物，就写了个脚本比对新旧两版编译器的输出文件——满屏 `identical=True`。差一点就信了。stderr 里全是「找不到路径」：求哈希的命令失败后返回空值，两个空值「相等」。重写的版本先算清楚「应该比对多少个文件」，数量不对、任何一个文件缺失、任何一次求哈希失败，都直接判失败。42 个文件逐一字节相同，这才叫证明。写任何检查时都问自己一句：**它怎样才会失败？它失败时，我看得见吗？**

**5. 独立评审：找一个不知情的人专挑毛病。** 代码、测试、教程都写完，门禁全绿之后，我请一位没有看过这段对话的评审者只做一件事：找反例。它用大约 770 个输入跑了将近一个小时，交回的清单里有：

- 两个我以为已经修好的级联：方法调用写了两次（`o.amount.abs() > 1 && o.score.abs() < 2`），第二个仍会报「未知算子」；条件里多一个逗号，会连带报出「期望记录绑定名」。
- 一句会撒谎的提示：`.filter(o.status = "paid")` 被提示「检查是否缺少右括号」。
- 两个从 M0 起就存在的崩溃与卡死：100 层嵌套的括号让编译器栈溢出；一行一万个非法字符要渲染一分钟以上。
- 这一章初稿里的过度宣称：「一次全部报出」并不总成立。

我自己的 84 个测试全绿，是因为**测试和实现有同样的盲区——我只会测到自己想到的情况**。处理每一条的流程都一样：先把它写成一条会失败的测试，再修实现，最后回来改教程。你现在读到的「残骸」和「别把调用栈撑爆」两节，都是这么来的。

请人评审有一个技巧：要求对方给**反例**——确切的输入，加上实际输出——而不是给评价。「这里可能有问题」没法下手；「这个输入会输出两条错误」可以立刻变成一个测试。

**6. 别给枚举变体起名叫 `None`。** 我给「不接受参数」这个变体起名 `None`，又在函数开头写了 `use Arity::*;`。于是模式匹配里的 `None` 有了两个候选——我的变体，和前奏库里的 `Option::None`——编译器把它们混在一起，报出一串莫名其妙的类型错误。改名成 `Empty` 就好了。前奏库里那些无处不在的名字（`None`、`Some`、`Ok`、`Err`）不要拿来做自己的变体名。

**7. 提交是唯一可靠的备份。** 评审进行期间，工作区里几个还没提交的源文件和这一章的初稿不见了。双方的工具调用记录里都找不到删除操作，原因没有查明。幸好运行环境把会话里的每一次读写都记了日志：我按顺序重放了自己的每一次 `write` 和 `edit`，把文件一字不差地找了回来，并用当时读文件留下的记录逐行核对过。这件事和编译器无关，却决定了这一章能不能交出来：**一段工作写完就提交，别攒着。** 顺便一说，找回的办法你并不陌生——只要「怎么算出来的」是确定的，结果就可以重新算一遍（第 5 章）。

三个错误各代表一种情形：`&` 是词法错误（它占住位置，没有引发任何语法错误）；`.select(` 那条是 `.extend({` 少了 `)`，恢复后 `.select` 照常解析，于是同一行里 `+` 后面缺操作数又被独立地找了出来。

再看几个常见笔误的消息（自己建文件试；位置行已省略，只留首行与提示）：

```text
error[PAR-004]: if 的条件不能放进 `{ }`
  提示: 写法: `if 条件 { 值 } else { 值 }`——条件写在第一个 `{` 之前

error[PAR-001]: `.filter(` 的参数到此已完整，不需要 `,`

error[PAR-001]: 期望 `)` 结束 `.filter(`，却先遇到了 `=`
  提示: 这个算子只接受一个参数：是多写了一个，还是把 `==` 写成了 `=`？

error[LEX-001]: 非法字符 `（`
  提示: 这是全角括号：请改用半角 `(` 和 `)`

error[LEX-001]: 非法字符 `;`
  提示: Pebble 的流水线靠 `.` 连接，不需要分号
```

第三条值得多说一句。`.filter(o.status = "paid")` 把 `==` 写成了 `=`。我的初版对「右括号的位置上不是右括号」一律提示「检查是否缺少右括号」——对这个错误来说那是实话的反面：括号一个不少。**提示是在替用户做判断，判断错了比不给提示更糟。** 所以 `expect_close` 现在先看遇到的是什么：到了文件结尾、下一个算子、或者一个不配对的右括号，才说「缺少右括号」；遇到标识符、字面量、`=`，就说「参数已经完整」。

倒过来也成立：`.filter(a, b)` 多写了一个参数，报的是「参数到此已完整，不需要 `,`」，同样不提缺少右括号。

## 练习

1. **先预测，再验证。** 把下面这个文件存成 `.pebble`，先在纸上写下你预期的错误列表（每条：错误码 + 行 + 列），再运行编译。对不上的地方，想清楚是预测错了还是实现错了（提示：共 4 个错误，其中两个在第 4 行；第 3 行那一个是 PAR-006，因为 `o.amount + 1` 没有 `as`）：

   ```pebble
   Table("tests/data/orders.csv") as o
     .filter(o.amount > 100 & o.score != null)
     .select(o.customer_id, o.amount + 1, o.typo
     .take(1.)
     .collect()
   ```

   值得琢磨的一点：第 3 行末尾漏了 `)`，但这条诊断报在**第 4 行** `.take(` 的 `.` 上。为什么不报在漏写的地方？（提示：解析器读到哪里，才第一次有证据说「这里少了个括号」？）

2. **残骸模式的出口。** 现在一旦进入残骸模式就保持到文件结尾，代价是：这之后真正拼错的算子名这一次不会被报出来。想一想：有没有比「保持到文件结尾」更好的退出条件？它会不会重新引入「残骸」一节的那种级联？把你的方案写成两个测试：一个证明它修好了什么，一个证明它没有弄坏什么。

3. **合并相邻的洞。** `|o|`（已废除的 Lambda）现在报两条 LEX-001，每个 `|` 一条。让相邻的 `Tok::Error` 合并成一条诊断。动手前先想清楚：合并的判据是什么——同一行且中间没有别的 token？会不会把两个本来独立的非法字符误合并？先写测试，再改实现。

4. **读 `sync_to`。** 解释这两句为什么缺一不可：(a)「比 `base` 更深的括号整组吞掉」；(b)「`base` 层的右括号不消费」。各构造一个输入，说明去掉其中一句后会多报或漏报什么。

5. **给「忘了写 `(`」更好的提示。** `.filter o.amount > 1)` 现在报「期望 `(`，遇到 标识符 `o`」——读者看到的是一个孤零零的 `o`，未必明白它指的是整条没加括号的表达式。请让消息带上算子名，并提示「参数要用 `(` 和 `)` 包起来」。提示：`expect_punct` 并不知道自己在哪个算子里——这个信息从哪里传进去？

6. **思考题：为什么恢复过的程序不做语义检查？** 用 `.extend({ x = o.typo }).filter(x > 0)` 说明：如果把坏的 `extend` 丢掉再做语义检查，会发生什么？要继续检查而不报假警报，语义层需要一种「什么都接受、但绝不报错」的类型——这就是第 9 章「毒化类型」的起点。

7. **挑战：错误预算。** 似乎对任意输入，解析器报告的错误数都不超过「token 数 + 1」。找出一个反例，或者证明它。提示：每报告一个错误，解析位置必须先前进到一个同步点；同步之后，下一次报告之前是否必然消费了至少一个 token？

8. **挑战：找你自己的反例。** 不看测试文件，给自己写 10 个「你觉得编译器会处理错」的输入，逐个运行。有哪怕一个的输出不是「恰好该报的错误」，就把它变成测试——这一章一半的内容就是这么来的。
