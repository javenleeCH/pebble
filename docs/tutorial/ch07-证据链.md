# 第 7 章 落地：build / run / verify 证据链闭环

> 对应文件：`crates/pebble-driver/src/{lib.rs, main.rs}`、`crates/pebble-hir/src/manifest.rs`。
> 编译器的价值在「跑起来还能被核对」的那一刻才成立——本章把前面六章的零件组装成一个**可演示、可篡改、可发现篡改**的系统。

## 本章目标

1. 组装四幕流程：build → 审批 → run → verify；
2. 实现 TOCTOU 防护（数据内容哈希）与 RUN-001 f64 预检；
3. 诚实划定证据链**证明什么、不证明什么**。

## 代码走读

### 数据模型：manifest 与 receipt

证据链的核心是两个 JSON 文件，回答两个不同的问题：

```rust
ExecutionManifest {            // build 时生成 ——「审的是什么」
    hir_hash,                  // canonical HIR 指纹（第 5 章）
    schema_lock_hashes,        // 编译针对的 Schema 工件
    dataset_identities,        // 数据定位符 + lock 哈希 + **内容哈希**
    artifact_hash,             // canonical SQL 的哈希（第 6 章）
    backend, engine_config,    // 引擎与配置（threads=1）也是被审内容
    terminal_options,          // 输出目标不可在 codegen 后偷加
}

ExecutionReceipt {             // run 时生成 ——「实际跑的是什么」
    manifest_hash,             // 本次执行绑定的已审 manifest
    submitted_artifact_hash,   // 实际提交的 SQL 工件哈希
    actual_engine,             // 实际引擎版本
    input_validation,          // RUN-001 预检结果
    status,                    // Ok / Failed{code, message}
}
```

verify 的逻辑只是三个相等比较：`receipt.manifest_hash == hash(审定的 manifest)`、`receipt.submitted_artifact_hash == manifest.artifact_hash`、（若 pin 了版本）引擎版本一致。**简单到可以在脑内审计**——这是有意为之：证据链的可信度来自它的可读性，复杂的安全机制没人看得懂就没法信。

## 四幕流程

```text
第一幕 build：源码 + locks → canonical HIR/hash + canonical SQL + manifest
第二幕 审批：人看 plan.algebra.tex / plan.sql，认可 manifest_hash（M0 的"审批"就是记下这个哈希）
第三幕 run：  TOCTOU 复核 → f64 预检 → 提交同一份 SQL → receipt
第四幕 verify：三个相等比较 → APPROVED PLAN == EXECUTED PLAN
```

```powershell
cargo run -p pebble-driver -- build examples/00_m0_revenue.pebble --locks tests/locks
cargo run -p pebble-driver -- run   examples/target/pebble/00_m0_revenue
cargo run -p pebble-driver -- verify examples/target/pebble/00_m0_revenue/manifest.json examples/target/pebble/00_m0_revenue/receipt.json
```

实测输出：

```text
2 行结果：
c2,2,12000
c6,1,11000
APPROVED PLAN == EXECUTED PLAN
```

## run 的五道关卡（按序执行）

1. **工件完整性**：重算 `plan.sql` 的哈希 ≠ manifest.artifact_hash → RUN-003（工件被篡改/损坏）；
2. **TOCTOU**：build 时记录了每个数据文件的内容哈希；run 时重算，不一致 → RUN-002。**路径是定位符不是身份**（第 5 章）在这里兑现——同一个路径、不同的字节，就是不同的输入；
3. **引擎定位**：找不到 duckdb → RUN-003（receipt 照写，绑定仍成立）；
4. **RUN-001 f64 预检**：对每个源 schema 的 f64 列跑 `NOT isfinite` 检查，在**任何表达式求值之前**执行（08 §8.3）——数据含 NaN/inf 是输入问题，不得静默变成 null，也不得伪装成程序错误；
5. **提交执行**：把 canonical SQL **原样**交给 DuckDB（stdin 脚本），捕获结果 → receipt。

失败的 run 也写 receipt——`status: failed` + RUN 码。**证据链不只记录成功**：一次被拒绝的执行同样是可核对的证据（数据被篡改的证明）。配套测试 `run_without_duckdb_writes_failed_receipt` 专门验证：status 失败时，manifest/artifact 绑定依然成立。

## 篡改实验（建议亲手做一遍）

```powershell
# A. 篡改数据 → RUN-002（改 tests/data/orders.csv 里任意一个数字，重新 run）
# B. 篡改 receipt → VERIFY FAILED（把 receipt.json 的 submitted_artifact_hash 改成任意值）
# C. 语义变更 → 旧审批失效（把 10000 改成 9999 重新 build，拿旧 receipt verify 新 manifest）
# D. 只改注释 → hash 不变（第 5 章规则的行为级验证）
```

对应的自动化测试：`crates/pebble-driver/tests/evidence_chain.rs` 里 8 个测试，其中端到端、TOCTOU、RUN-001 和「`extend` / `join` 直接接在源后面」四个在真实 DuckDB 上执行。最后那个是补上的教训：样例 02 曾经「能编译」却生成坏 SQL，因为没有任何测试真正执行过它（第 6 章）。

## 诚实边界：证据链证明什么

这是本章最重要的一节，直接抄自保证矩阵（design-decisions §1.2）：

**证明了**：源码 → canonical HIR 的确定性；Schema/数据/工件/配置与本次执行请求的密码学绑定；格式与注释不影响指纹；数据与工件篡改可检测。

**没证明**：执行结果正确（编译器与 DuckDB 在信任基内）；外部引擎物理计划等于 HIR（DuckDB 自己重写）；跨版本一致性；资源安全（终止 ≠ 有界内存）。

为什么这个边界是**美德而不是缺憾**？因为夸大的安全声明本身就是安全漏洞。第二轮评审原话：「如果这三件事做不出来，『可信数据变换』只是更高级的话术」——M0 把三件可证伪的事做到了：**威胁模型（RUN 码体系）、保证矩阵（manifest 字段）、单后端证据链（四幕）**。

## 工程细节三则

**1. DuckDB 调用**：`duckdb -batch -csv -noheader`，SQL 走 stdin（避免命令行长度限制），版本探测走 `SELECT version`。`tools/duckdb.exe` 不入库（.gitignore），测试在缺失时自动跳过。

**2. 输出摘要**：collect/print 打印行数 + 前 11 行；write 验证输出文件存在。摘要不进 receipt 的绑定范围（它是给人看的，不是证据）。

**3. Windows 路径**：`tests/data/orders.csv` 正斜杠在 Pebble 字符串字面量、lock 身份、DuckDB `read_csv` 三处保持一致——反斜杠会撞上字符串转义（LEX-003）。跨平台教训：**测试 fixture 里的路径一律正斜杠**。

## 练习

1. **签名**：用 ed25519 给 manifest 签名（`signature` 字段 + `--signing-key`），verify 校验签名。当前哈希只保证**一致性**，不保证**真实性**——想清楚签名解决的是威胁模型里的哪一格。
2. **receipt 挑战**：构造一个攻击场景：攻击者能改 plan.sql、receipt.json、数据文件中的**任意一个**，但不能改 manifest——哪些攻击被挡住？哪些挡不住？写出攻防矩阵。
3. **--pin-duckdb**：实现已在 build（pin 版本进 manifest）与 verify（版本比对）就位。补端到端测试：pin 一个错误版本 → run 成功但 verify 失败。
4. **重放**：同一 manifest 连续 run 两次，两次 receipt 应仅在时间性字段上不同。想清楚：为什么这很重要？（提示：审批一次、执行多次的合法场景）
