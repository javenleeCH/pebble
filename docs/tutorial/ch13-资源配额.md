# 第 13 章 资源配额与威胁模型（M3）

> 对应文件：`crates/pebble-driver/src/budget.rs`、`crates/pebble-hir/src/lock.rs`（max_rows）、
> `crates/pebble-hir/src/manifest.rs`（预算/配额/memory_limit）、`crates/pebble-duckdb/src/lib.rs`（memory_limit 前言）、
> `crates/pebble-driver/src/lib.rs`（cmd_build quota / cmd_run timeout / OOM 分类）、`docs/threat-model.md`。
> 前置阅读：ch00 红线第 1 条「终止不等于资源安全」。

## 本章目标

1. 把「必然终止」升级为「有界资源」——这是红线第 1 条欠的债；
2. 实现静态成本模型：从 lock 的 max_rows 推导最坏情况输出行数；
3. 实现配额（build 时拒绝）、超时（run 时杀引擎）、内存上限（进 canonical SQL 前言）；
4. 把威胁模型写成可测试的文档，而不是安全话术。

## 为什么非图灵完备给了你成本上界

红线第 1 条说「无用户递归 → 必然终止」。但一个 100 行表 cross join 一个 100 行表产生 10000 行——它**终止了**，只是吃光了你的内存。两轮评审都指出了这个洞：

> 「必然终止」只是数学性质；平台需要的是可中断、可计量、可归责的有界执行。

修补的钥匙就藏在同一份有限性里：**所有迭代绑定有限集合 → 输出规模是输入规模的函数 → 这个函数可以静态计算**。通用语言做不到这一点（一个 `while` 循环的输出规模取决于逻辑），Pebble 可以。这是 DSL 的结构性优势第一次兑现成安全机制。

## 代码走读

### 静态成本模型（budget.rs）

核心洞察是**只有一个乘法算子**：join。其余算子要么传递行数（filter/sort/extend/select），要么收窄（take），要么消减（聚合）：

```rust
// budget.rs — 逐节点最坏情况
match kind {
    TransformKind::Take { n } => left.map(|l| l.min((*n).max(0) as u128)),
    TransformKind::Join { .. } => match (left, right) {
        (Some(l), Some(r)) => Some(l.saturating_mul(r)),   // 唯一乘法
        _ => None,
    },
    _ => left,                                            // 行级算子不放大
}
```

全局聚合返回 `Some(1)`——空输入恰好一行（第 4 章的语义在这里派上用场）。聚合分组返回输入上界——组数不可能超过行数。全用 `u128` 饱和算术：**宁可高估，不可低估**。

max_rows 放在 Schema lock 里而不是运行时统计——**它是承诺不是猜测**。声明 max_rows=N 的宿主必须保证数据不超过 N 行（进 lock 主体哈希——虚报会破坏 lock 完整性）。静态预算的可信度等于宿主承诺的可信度，这句话写进了 `budget.rs` 的模块注释。

### 配额进 manifest，成为被审内容

`--quota-rows N` 的设计决策值得停下来讲：

1. **拒绝发生在 build 期**——审批者根本看不到超配额的计划，攻击在源码阶段就被挡住；
2. **预算和配额都写入 manifest**（`estimated_max_output_rows` / `quota_rows`）——审批者签名前能看到最坏情况，**成本模型是审批信息的一部分**；
3. **缺 max_rows 的源 + 配额 → 拒绝**（不静默降级）：宁可让用户补 lock，也不悄悄放过。

### 超时杀引擎

`std::process` 没有带超时的 `wait()`——所以轮询 `try_wait`，到期 `kill()`：

```rust
let deadline = timeout.map(|t| std::time::Instant::now() + t);
let status = loop {
    match child.try_wait() {
        Ok(Some(st)) => break Some(st),
        Ok(None) => {
            if deadline.is_some_and(|d| Instant::now() >= d) {
                let _ = child.kill();          // 宁可取消，不可失控
                break None;
            }
            std::thread::sleep(Duration::from_millis(100));
        }
    }
};
```

`TimedOut` 与普通 `Err` 分开建模：receipt 里前者归 RUN-004（资源），后者归 RUN-003（IO）。**分类的精确度决定攻击的定位精度**。

### OOM 归类

DuckDB 触发 memory_limit 时的报错包含 "Out of Memory" / "memory limit"——正则不引依赖，字符串匹配：

```rust
fn classify_engine_failure(stderr: &str) -> RunCode {
    let lower = stderr.to_ascii_lowercase();
    if lower.contains("out of memory") || lower.contains("memory limit") || lower.contains("oom") {
        RunCode::ResourceExhausted
    } else {
        RunCode::IoFailure
    }
}
```

### memory_limit 进 canonical SQL 前言

`SET memory_limit = '512MB';` 紧跟 `SET threads TO 1;` 进 canonical SQL。运行时资源上限与线程数一样属于**被审内容**——审批者签名前就能看到「这次执行最多用多少内存」。这两个配置不是可调参数：改它们 = 改计划 = 改哈希。

### 超时序契约

**build → sign → run → verify** 的顺序在 ch12 的基础上增加了一个理由：`--timeout-secs` 是 **run 的参数**而不是 build 的——它是执行侧的策略，不是计划的一部分。但 memory_limit 是 build 的（进 canonical SQL / manifest）。区分：**引擎配置（计划的一部分）vs 执行策略（宿主的选择）**。

## 预算↔配额一致性进 verifier

第七项检查：manifest 的预算与配额必须自洽（预算 ≤ 配额；有配额必须有预算）。篡改配额向上 → 签名核验失败（ch12 兜底）+ 预算检查亮红（本章兜底）。

## 跑起来

```powershell
# 攻击演示：cross join 预算超限
# 造两个 100 行的 lock，配额 50
cargo run -p pebble-driver -- lock table a.csv id:i64 name:string --max-rows 100 --out lock0.json
cargo run -p pebble-driver -- lock table b.csv id:i64 name:string --max-rows 100 --out lock1.json
"Table(`"a.csv`") as x`n  .join(Table(`"b.csv`") as y, on = x.id == y.id)`n  .collect()" | Set-Content cross.pebble
cargo run -p pebble-driver -- build cross.pebble --locks . --quota-rows 50
# 预期：SEM-018 最坏情况输出约 10000 行 > 配额 50 行

# 超时演示（需 duckdb）
cargo run -p pebble-driver -- run examples/target/pebble/00_m0_revenue --timeout-secs 0
# 预期：RUN-004 执行超时，引擎进程已被终止

# 全量测试（含 9 个预算/配额/超时/OOM 测试）
cargo test -p pebble-driver --test budget
```

## 诚实边界

- **静态预算是上界不是精确值**：cross join 的真实结果可能远小于 n×m，但上界宁可松也不可漏——这是静态分析的一般规律；
- **超时杀进程是粗暴的**：进程级的取消没有优雅回滚——被杀的进程可能留下临时文件（DuckDB 的 .tmp）；清理是宿主部署层的责任；
- **memory_limit 不防所有 OOM**：DuckDB 的内存管理有内部缓冲——防大部分，不防全部；
- **威胁模型覆盖编译/执行边界，不覆盖部署边界**：网络、沙箱、进程隔离是平台层的责任，文档明说。

## 练习

1. **扩展预算规则**：`group_by` 后再 `join` 一个源——预算是多少？推导公式并写测试钉住（提示：分组后的上界是「组数 ≤ 输入行数」，但 join 是左 × 右不是「分组数 × 右」……等等，是吗？）。
2. **max_rows 的可信度**：宿主虚报 max_rows 会发生什么？lock 主体哈希保证了 lock 文件不被篡改，但没保证宿主声明的数字是真实的。设计一个防线（提示：build 时对存在的数据文件做行数统计，与声明比对——想清楚：为什么这不能完全替代信任？）。
3. **执行侧签名**（M4 议题预热）：receipt 说「我执行了这份计划」，但谁证明执行环境的身份？给 receipt 也加 ed25519 签名（执行侧密钥），verifier 验双签名。与审批签名的威胁模型差异：一个防假审批，一个防假执行。
4. **预算可视化**：`pebble build` 输出「最坏情况」时加一个人类可读的量级提示（如 `~10^4 行`）。查阅 u128 格式化并写测试。
