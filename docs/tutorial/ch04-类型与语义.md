# 第 4 章 类型系统与 P0 语义：null、Kleene、checked-null 与流敏收缩

> 对应文件：`crates/pebble-semantics/src/lib.rs`；规范：`docs/draft/spec/04/05/07`。
> **这是全书最核心的一章**：一门语言「说得清说不清自己每一步的行为」在此分野。

## 本章目标

1. 实现「严格 null 传播 + 判空测试 + Kleene 三值逻辑」这套组合拳；
2. 让可能失败的表达式在**静态类型上可空**（checked-null），编译期可确定的失败直接拒绝（SEM-016）；
3. 实现流敏非空收缩 NN(p)——`filter(f != null)` 之后 `f` 变成非空类型；
4. 按上下文推导聚合返回类型。

## 为什么从 null 开始

null 是「语义封闭」红线的第一个战场。规范曾写「null 的取值行为由算子实现定义」——两轮评审指出这直接摧毁可数学化主张（同一个表达式在不同后端有不同取值，导出的公式就不是公式）。P0 修复的第一条就是把它定死：

> **除判空测试与逻辑连接词外，一切运算严格传播 null；判空 `x == null` 是独立语法形式，恒返回非空 bool。**

## 三件套的实现

**1）严格传播**：`resolve_binary` 里，算术/比较的任何一侧是 null → 结果 null。类型上，普通比较**一律 `?bool`**：

```rust
(BinOp::Eq | BinOp::Neq, _, _) if ... => Opt(Box::new(Bool)),
```

为什么不是「两侧非空时返回 bool」？因为静态类型不能依赖数据：`a == b` 在 `a` 为 null 的行上是 null——类型系统必须诚实地把这个可能性编码进去。

**2）判空测试**：`x != null` 不走普通比较，lowering 为 `Unary(Not, Call(IsNull, x))`，类型恒 `bool`。这一步发生在**语义层**，后端（第 6 章）看到的是 `IS NOT NULL`——SQL 的 `x = NULL` 陷阱从根上绕开。`null == null` 更特殊：直接折叠为常量 `true`。

**3）Kleene**：`&&`/`||` 是严格传播的**显式例外**——`false && null = false`，`true || null = true`。短路是实现自由，真值表是契约：

```rust
let ty = if l.ty().is_opt() || r.ty().is_opt() { Opt(Box::new(Bool)) } else { Bool };
```

DuckDB 的 `AND`/`OR` 恰好就是 Kleene——但这是运气，不是设计。第 6 章会看到那些**不**match 的地方怎么补。

## checked-null：类型必须先于运行时撒谎

spec 的规则：**可能失败的运算，其静态返回类型必须可空；禁止声明 i64 运行时却产出 null**。

```rust
(BinOp::Add, I64, I64) => Opt(Box::new(I64)),   // 溢出可能
含 f64 的算术           => Opt(Box::new(F64)),   // 非有限结果可能
一元 `-`: f64           => F64                  // 有限取负仍有限 → 不需要 opt！
```

注意第三行：`-x`（f64）返回**非空** f64——因为有限值取负永远有限，不需要为它付可空的代价。类型规则要精确到「这个失败模式在这个运算上存在与否」，一刀切的「算术都可能失败」是懒人规则。

**null 字面量的归属**是本函数里最绕的部分：`1 + null` 里 null 该是什么类型？答案是**由另一侧推导**（`?i64`）。所有可能消费 null 的位置（二元、if 分支、函数实参）都带一个「基类型上下文」`resolve_with_base`；两侧都是 null（`1 + null` 不算，`null + null` 算）或裸 `x = null` → SEM-008。

## SEM-016：常量在编译期就得诚实

`filter(1/0 > 2)`：整个谓词是常量且必然失败 → **编译错误**。但 `filter(1/0 > o.amount)`：`1/0` 是常量子表达式，运行时按 checked-null 返回 null（`null > x` → null → 不保留行）——**合法**，不诊断。

```rust
fn const_domain_check(&mut self, e: &THirExpr) {
    if self.const_failed || !e.is_const() { return; }   // 只有全常量才报
    if let Err(span) = const_val(e) { ... SEM-016 ... }
}
```

区分标准只有一条：**「编译期可确定」= 求值路径与数据无关**。`if false { 1/0 } else { 1 }` 也不报错——未选中的分支不求值，语义上不存在失败。

## NN(p)：流敏非空收缩

最有差异化的一条规则。动机：`filter(s.score != null)` 之后，`s.score` 显然不可能再是 null——类型系统应该兑现这个常识：

```text
NN(f != null)           = {f}          （判空守卫）
NN(a && b)              = NN(a) ∪ NN(b)  （合取：都要成立 → 保证取并集）
NN(a || b)              = NN(a) ∩ NN(b)  （析取：一侧成立即可 → 取交集）
NN(if c {a} else {b})   = (NN(c) ∪ NN(a)) ∩ (else 路径的保证)
```

else 路径的细节体现「可靠但不完备」的克制：只有当 `c` 恰好是 `is_null(f)` 时，else 分支才继承 `{f}`（`is_null` 为假 ⇒ f 非空）；其他否定形式**不猜测**。所以：

- `filter(f != null || g > 0)` **不**收缩 f（析取交集为空）——这是语义正确的保守；
- `filter(f != null && f > 0)` 收缩 f；
- `filter(f > 0)` **不**收缩 f，即使运行时只有非空 f 能通过——MVP 明确不做这种隐式推导，规范里写明「可靠但不完备」。

把「我们没做聪明到什么程度」写进规范，和把做了什么写进去一样重要。

收缩只作用于**当前 filter 的输出 Schema**，不跨算子逆向传播：`extend({ g = f }).filter(g != null)` 不会顺带收缩 f——跨表达式等价推理是未来的 opt-in 特性，不是默认行为。

## 聚合签名：三因素推导

聚合返回类型不是按函数名硬编码，而是由三问推导：

```text
全局组可能为空吗？  参数可能全 null 吗？  计算可能溢出吗？
```

| 签名 | 结果 |
|---|---|
| `count()` / `count(x)` | 恒 `i64`（空全局组 = 0） |
| 分组聚合 + 非空参数的 `min/max` | `T`（组内至少一行且非空） |
| 全局或可空参数的 `min/max/avg` | `?T` / `?f64`（空全局组 = null） |
| `sum` 任何情况 | `?T`（空集合 null + 整数和可能溢出） |

单测 `agg_signatures_follow_context` 验证：同一棵 HIR 里 `count` 得 `i64`、`sum(?i64)` 得 `?i64`、分组的 `min(?i64)` 得 `?i64`。这些类型直接进入 HIR（第 5 章）与 SQL 守卫（第 6 章），是「审的那份」的一部分。

## 空输入语义

- 分组聚合：空表 → **零组零行**（不凭空造组）；
- 全局聚合：空表 → **恰好一行**（空全局组），`count()=0`、其余 null。

这两条让「全局聚合」和「分组聚合」在边界数据上行为可预测——测试矩阵里必须有它们。
