# 第 9 章 语义层错误恢复：毒化，让坏消息静默传播

> 对应文件：`crates/pebble-semantics/src/lib.rs`；规范：`docs/draft/spec/08-diagnostics.md` §8.6 第 3 条。
> 测试：`pebble-semantics` 的单测（`codes` 系列）、`crates/pebble-driver/tests/diagnostics.rs`。

## 本章目标

1. 看清语义阶段为什么比解析阶段难恢复：这里的错误会**改变下游看到的世界**；
2. 学会教科书里的**毒化**（poison）：让一个失败的定义「存在但坏了」，它的后果不再被报成错误；
3. 分清三种失败——可以带着走的、必须沉默的、只能停下的；
4. 再体会一次「同一个思想换个地方」：第 8 章的同步点和残骸，在这一章各自对应什么。

## 为什么：解析器的办法到这里不够用

先看一个文件，它有两处拼写错误（就是本章「跑起来」用的演示文件）：

```pebble
Table("tests/data/orders.csv") as o
  .extend({ total = o.amont + 1 })
  .filter(total > 0)
  .filter(o.statuz == "paid")
  .collect()
```

第 9 章之前的编译器只报第一个：

```text
error[SEM-001]: 字段 `o.amont` 不存在于当前解析域
  ┌─ multi_semantic_error.pebble:4:21
  │
4 │   .extend({ total = o.amont + 1 })
  │                     ^^^^^^^ SEM-001
  │
  提示: 当前可见字段: amount, customer_id, order_id, score, status
编译中止：共 1 个错误（SEM 1）
```

和第 8 章开始时一模一样的循环：改一个、编译一次、看下一个。

那把第 8 章的办法搬过来——「坏掉的算子整个丢弃，继续下一个」——行不行？试试就知道了。`extend` 失败被丢掉之后，轮到 `.filter(total > 0)`：`total` 这个名字**从未被定义过**，于是编译器报「字段 `total` 不存在」。

可这一行用户写得没错。错的是上一行。这就是**级联错误**在语义层的样子：它比解析层更隐蔽，因为那条消息单看是完全成立的。

### 为什么语义层更难

| | 解析器（第 8 章） | 语义层（本章） |
|---|---|---|
| 每个算子依赖什么 | 只依赖 token 的形状 | 依赖**上游算子的输出 schema** |
| 一个算子坏了，留下的是什么 | 一段谁也不看的残骸 | 一个**变了的世界**：某些名字不存在了，或者类型变了 |
| 最坏的情况 | 把残骸当成算子 | 把「世界的改变」当成用户新的错误 |

所以语义层的恢复多了一件事：**失败之后，要替下游把世界补齐**——至少补到「哪些名字坏了」这一步。这就是毒化要解决的问题。原则还是那一条：

> **一个根因只报一次。拿不准是不是后果时，宁可少报，不可多报。**

### 被否决的备选

| 方案 | 为什么不行 |
|---|---|
| 维持首错即止 | 正确，但 N 个错要编译 N 次 |
| 失败的算子丢掉，流水线照常往下 | 下游引用它的输出名字，全是假 SEM-001 |
| 失败的算子丢掉，**后面的算子全部跳过** | 没有级联了，但下游独立的错误也全被吞掉 |
| 给 HIR 的类型加一个 `Poison` 变体，让它随类型流动 | 「毒化」这种只在前端恢复期间才有意义的状态，就能进入被审批、被执行的 HIR，得靠事后检查去拦。**能不让它出现，就不要靠检查**（第 2 章） |
| 碰到坏名字时报一条「这里用了一个失败的定义」 | 仍然是每个使用处一条噪音 |

## 代码走读

### 1. 先把失败分成三类

恢复策略的全部内容，就是下面这张表。读代码时对号入座即可。

| 情形 | 怎么处理 | 例子 |
|---|---|---|
| 算子里**一个独立的元素**失败 | 报错；它的输出名字被毒化；**算子不发射**；继续 | `extend` 里某一个绑定的右边拼错了 |
| 一个表达式**引用了毒化的名字** | **沉默**：不报错，直接失败 | `.filter(total > 0)` |
| 数据源的 schema **未知** | **停下**：整个语义阶段到此为止 | 数据源缺少 Schema lock（SCH-001） |

第一类对应第 8 章的「列表循环」：`extend` 的每个绑定、`select` 的每一项、`agg` 的每个键与绑定、`sort` 的每个键，都是相互独立的元素，一个失败不影响检查其余的。

第三类为什么要停下？表的形状都不知道，后面每一个算子都无从检查——再往下走只会制造噪音。

### 2. 毒化表：让失败的名字「存在但坏了」

关键的决定是：**定义失败的名字，不删掉，而是留一个占位**。

```rust
    fn poison_field(&mut self, name: &str, node: NodeId) -> FieldSchema {
        let id = self.fresh_field();
        self.poisoned.insert(id);
        FieldSchema {
            id,
            name: name.to_string(),
            ty: Type::Opt(Box::new(Type::I64)),
            origin: FieldOrigin::Derived {
                node,
                binding: name.to_string(),
            },
        }
    }
```

两样东西：输出 schema 里的一个占位字段，加上毒化表 `poisoned`（一张字段 id 的集合）里的一个条目。

为什么要占位？因为下游多半会引用这个名字。如果直接删掉，下游的 `.filter(total > 0)` 就会走到「字段 `total` 不存在」那条路上——那正是我们要避免的假错误。占位让 `total`「存在」，而毒化表记录着它「坏了」。

那占位的类型填什么？**无所谓**。`Type::Opt(Box::new(Type::I64))` 只是填空：任何碰到毒化名字的表达式，在走到类型检查之前就已经停下了（下一小节）。所以这个类型永远不会被读取。写代码时最怕的就是「这里填什么都行」——所以要写注释说清楚为什么行，再用测试钉住它确实不被读。

毒化表只有一张，全程只增不减。一个名字坏了就是坏了，直到这次编译结束。

### 3. 解析字段：毒化的名字「不可见」

毒化在哪里生效？在**唯一一个把名字变成字段的地方**——`resolve_field`。所有表达式最终都要经过它去取字段，所以只需要改这一处。看裸字段名（不带别名）的查找：

```rust
                let raw = env.by_name(name);
                if !raw.is_empty() && raw.iter().all(|f| self.poisoned.contains(&f.id)) {
                    return None;
                }
                let matches: Vec<&FieldSchema> = raw
                    .into_iter()
                    .filter(|f| !self.poisoned.contains(&f.id))
                    .collect();
```

三步：

1. `raw`：schema 里叫这个名字的**全部**字段，包括毒化的占位；
2. 如果它们**全是**毒化的——这个名字指向的正是一个失败的定义——**沉默地停下**：`return None`，不报告任何东西；
3. 否则把毒化的滤掉，只用真实存在的字段继续往下走（唯一、歧义等判断照旧）。

第 2 步为什么要单独存在，而不是直接滤掉之后交给后面处理？因为后面还有一段「区分 SEM-001 与 SEM-012」的逻辑（第 3 章）：找不到字段时，它会去翻历史 schema，看这个名字是否「曾经存在过」——而**占位本身就在历史里**。不先拦下，`total` 就会被报成 `SEM-012 超出当前作用域`。这个坑是我写第一版时真踩过的，见文末「踩坑实录」。

「沉默」在这里有个精确的含义：**返回 `None`，但不往诊断袋里放任何东西**。而 `None` 会像以前一样被 `?` 一路传上去。于是不需要改任何函数的签名——见下一小节。

### 4. 算子层：逐个元素接住 `None`

解析器那边接住 `None` 的是流水线循环和列表循环；语义层这边，接住它的是算子处理逻辑里的 `match`。以 `extend` 的绑定为例：

```rust
                    for (idx, b) in record.bindings.iter().enumerate() {
                        if !is_first(idx) {
                            continue;
                        }
                        match self.resolve_expr(&b.value, &current_schema, false) {
                            Some(value) => {
                                self.const_domain_check(&value);
                                let output = self.fresh_field();
                                hir_bindings.push(pebble_hir::Binding {
                                    output,
                                    name: b.name.clone(),
                                    value,
                                });
                            }
                            None => {
                                failed.insert(b.name.clone());
                            }
                        }
                    }
```

以前这里是 `self.resolve_expr(…)?`——第一个失败的绑定就让整个 `extend` 作废。现在每个绑定自己面对成功或失败：成功的进 `hir_bindings`，失败的名字进 `failed`。循环结束之后：

- 有失败的绑定 → **不发射节点**，但照常构造输出 schema：成功的绑定给出真实字段，失败的名字给出毒化占位（`poison_field`）；
- 全部成功 → 和以前完全一样，发射节点。

`select`、`sort`、`agg` 是同一个形状。`filter` 没有列表，所以更简单——把 `?` 换成 `if let`：

```rust
                    if let Some(resolved) = self.resolve_expr(pred, &current_schema, false) {
                        if self.check_predicate(&resolved).is_some() {
```

谓词解析不出来，或者不是 bool：这一层 `if` 不进去，算子就不发射，schema 保持原样。

### 把演示文件走一遍

| # | 读到 | 发生了什么 | 毒化表 |
|---|---|---|---|
| 1 | `.extend({ total = o.amont + 1 })` | `o.amont` 不存在 → **SEM-001**。绑定失败：`total` 占位并毒化；`extend` 不发射 | `{ total }` |
| 2 | `.filter(total > 0)` | 解析 `total`：候选全是毒化的 → **沉默**。`filter` 不发射 | `{ total }` |
| 3 | `.filter(o.statuz == "paid")` | `o.statuz` 不存在 → **SEM-001**。这是一个独立的错误，和第 1 行无关 | `{ total }` |
| 4 | 文件结尾 | 两个错误，没有 HIR | |

注意第 2 行与第 3 行的区别：同样是一个「找不到的名字」，第 2 行是**后果**，第 3 行是**根因**。区分它们的全部依据，就是那张毒化表。

### 5. 一个设计上的回头：本来不必要的大改

我最初的计划是把语义层所有的 `Option<T>` 改成 `Result<T, 失败种类>`，用两种失败值来区分「已经报告过的」和「毒化的」。估算下来要动十几个函数、五十来个出错点。

动手前多问了一句：**到底谁需要区分这两种失败？** 逐个一看：算子层对它们的处理完全一样（都不发射、都把名字毒化、都继续）。整个系统里唯一需要区分它们的地方，就是 `resolve_field`——而它靠查一下毒化表就解决了。

于是函数签名一行没改，`?` 照旧。这是本章最想让你带走的一条经验：**动手之前，先找到真正需要那份信息的人。** 很多「必须的大改」，是因为把信息送到了不需要它的地方。

### 6. 同一个表达式里的两个错误

`extend` 的两个绑定相互独立，所以能各报各的。那同一个谓词里的两个拼写错误呢？

```pebble
  .filter(o.typo_a > 1 && o.typo_b < 2)
```

`&&` 两边的类型互不依赖（都是 bool），所以可以各解析各的：

```rust
            // 两侧的类型互不依赖：各自解析，两侧的错误都能报出来。
            //（连着写两个 `?` 的话，第一个错误就会让第二个还没检查的表达式被跳过）
            let l = self.resolve_with_base(left, env, Some(Bool), in_join_on);
            let r = self.resolve_with_base(right, env, Some(Bool), in_join_on);
            let (Some(l), Some(r)) = (l, r) else {
                return None;
            };
```

这里有一个值得记住的区分：Pebble 的 `&&` 在**求值**时会短路，但在**检查**时不能短路——右边没被选中执行，不代表它不需要被检查。只有类型互不依赖的运算符才能这样做；`a + b` 这类，左边的 null 字面量要靠右边的类型来定，所以仍然按顺序解析。

### 7. 其余的算子

| 算子 | 独立的元素 | 失败之后 |
|---|---|---|
| `extend` | 每个绑定 | 名字毒化；节点不发射 |
| `select` | 每一项 | 名字毒化；节点不发射。**裁剪作用域的语义不变** |
| `sort` | 每个排序键 | 节点不发射（schema 本来就没变） |
| `agg` / `group_by` | 每个分组键、每个绑定 | 名字毒化；节点不发射 |
| `filter` / `join` 的 `on` | （单个表达式） | 节点不发射；schema 不变 |
| `join` 的右表缺 lock | — | **停下**（未知 schema） |
| `group_by` 后面没有 `agg` | — | 报 SEM-005，跳过这个 `group_by`，继续 |

`select` 那一行值得多说一句。`select` 坏了一项之后，被它裁掉的字段对下游来说**确实不存在了**——这是用户写的 `select` 的本意，和那一项的失败无关。所以后面再引用被裁掉的字段，仍然报 SEM-012。这条规则由测试 `a_broken_select_still_cuts_the_scope` 钉住。

### 8. 最后一道防线：不允许沉默的失败

毒化靠的是「不说话」。一个副作用是：如果代码里还有别的某处会不说话地失败，它就会被当成毒化悄悄吞掉——用户面对一个没有任何诊断的失败。所以编译入口处加了一道检查：

```rust
    match result {
        Some(hir) => Some(hir),
        // 没有诊断却没有结果：这是编译器自己的 bug。不能让用户面对一个沉默的失败
        None => {
            diags.push(pebble_diagnostic::Diagnostic::error(
                Code::SemOpPosition,
                "内部错误：语义检查中止，但没有产生任何诊断",
                Span::new(0, 0),
            ));
            None
        }
    }
```

「沉默」只能是毒化的特权。别的任何失败都必须说话。

## 踩坑实录

**1. 占位进了历史，毒化被误报成 SEM-012。** 第一版实现里，毒化的查找只是「把占位滤掉」。新写的 12 个测试里立刻红了 3 个：`.filter(total > 0)` 被报成「`total` 超出当前作用域」。原因在上一小节说过——`resolve_field` 找不到字段时会去翻历史 schema，而占位就躺在历史里。「沉默」要做就要做到底：**在产生后果的那一步之前停下，而不是在半路上。**

**2. 提示推荐了一个坏掉的名字。** 测试全绿之后我跑了真实的 `pebble build` 看输出，发现第二条诊断的「当前可见字段」里赫然列着 `total`。错误消息本身没问题，是**提示**在误导。教训：加一个机制时，把它会流经的**每一条输出通道**都过一遍——诊断、提示、汇总行。

**3. 测试要两个方向都有。** 新测试里，「多个错误一次报完」那 8 条，在旧实现（首错即止）上会失败；而「毒化的名字不再报」那几条，在旧实现和正确的新实现上**都**通过——因为旧实现根本走不到那里。它们防的是相反方向的错误：一个天真的多错误实现会过度报告。事实上正是它们抓住了第 1 条里的 bug。只测一个方向的测试，只防一半的回归。

**4. 先问「谁需要这份信息」。** 见代码走读第 5 节。

## 练习

1. **先预测，再验证。** 下面的文件有 4 个错误、3 种不同的码。先在纸上写下每一处的错误码和行号，再运行：

   ```pebble
   Table("tests/data/orders.csv") as o
     .group_by(o.customer)
     .agg(
       orders = count(),
       revenue = sum(o.amont),
       avg_score = avg(o.status),
     )
     .filter(o.amount > 0)
     .collect()
   ```

   想一想：最后一行为什么是 SEM-012 而不是 SEM-001？它和 `agg` 里的那些错误有关系吗？

2. **函数实参**：`round(o.typo_a)` 只有一个参数所以没事；但如果有两个实参 `f(o.typo_a, o.typo_b)`，第一个失败后第二个就不会被检查了。照 `&&` 的写法改 `resolve_call`，让每个实参各自解析。先写测试。

3. **if 的三个部分**：`if o.typo_a { o.typo_b } else { 1 }`——条件、then、else 三者哪一些可以独立解析？（提示：then 与 else 的类型要统一，但*解析*可以各自进行。）

4. **思考题：缺 lock 为什么是致命的？** 现在右表缺 lock 时整个语义阶段停下。能不能只跳过依赖那张表的算子，继续检查其余的？代价是什么？你愿意为「多报几个错误」付出这份复杂度吗？

5. **两种毒化**：本章用「占位 + 一张表」表达毒化，另一种经典做法是在类型里加一个 `Poison` 变体。分别说出：各自怎么保证毒化状态不会进入被审批的 HIR？哪一种是靠类型系统保证的，哪一种是靠检查保证的？

6. **挑战：放宽第 8 章的门控。** 现在「解析阶段恢复过的程序不做语义检查」。但恢复出来的 AST 里，**第一个缺口之前**的算子是完整的、不受后面影响的。让语义层检查这一段前缀，需要 `PartialAst` 提供什么信息？哪些情况下前缀为空？
